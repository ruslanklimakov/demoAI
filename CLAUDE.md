# demoAI — AI-Augmented QA Playbook

> Этот файл автоматически читается Claude Code в каждой сессии.
> Здесь описаны правила работы AI-агентов в проекте.

## 1. Контекст проекта

Это демо-проект для интервью, цель — показать полный AI-augmented QA процесс:
от анализа требований в Jira до автоматизации, PR и регрессии.

**Тестируемое приложение (SUT):** https://demoqa.com/

## 2. Технологический стек

- **Автотесты:** Playwright + TypeScript
- **Архитектура:** Page Object Model
- **Тест-раннер:** `@playwright/test`
- **Отчётность:** встроенный HTML reporter + Allure (опционально)
- **CI:** GitHub Actions
- **Тест-менеджмент:** Jira (проект DEMOAI)

## 3. Структура проекта

```
demoAI/
├── tests/
│   ├── pages/          # Page Objects — селекторы и действия
│   ├── specs/          # Сами тесты (.spec.ts)
│   ├── fixtures/       # Тестовые данные и кастомные fixtures
│   └── utils/          # Хелперы (генерация данных, API-клиенты)
├── test-cases/         # Ручные тест-кейсы в Markdown/Gherkin (по тикетам)
├── risks/              # Risk-анализы по тикетам
├── exploration/        # Скриншоты и заметки exploratory-сессий
├── .claude/
│   ├── commands/       # Slash-команды для повторяющихся флоу
│   └── agents/         # Описания subagents (QA-аналитик, ревьюер и т.д.)
├── .github/workflows/  # CI: запуск тестов + Claude Code Action
└── CLAUDE.md           # Этот файл
```

## 4. Workflow для любой QA-задачи из Jira

Когда я (пользователь) даю команду вида *«Возьми в работу SCRUM-X»*, ты:

1. **Читаешь тикет** через `atlassian` MCP — берёшь summary, description, acceptance criteria, комментарии.
2. **Анализируешь требования критически** — выявляешь неоднозначности, противоречия, недосказанное. Если требования слишком размыты — задаёшь мне уточняющие вопросы и НЕ идёшь дальше, пока я не отвечу.
3. **Изучаешь SUT** через `playwright` MCP — открываешь релевантные страницы, исследуешь поведение, делаешь скриншоты ключевых состояний в `exploration/{TICKET}/`.
4. **Генерируешь риск-анализ** → `risks/{TICKET}.md`. Категории: functional, security, performance, accessibility, UX, data integrity. Для каждого риска — вероятность × impact.
5. **Пишешь тест-кейсы** → `test-cases/{TICKET}.md` в Gherkin. Покрытие: happy path, negative, boundary, security, accessibility. Каждый кейс с приоритетом P0/P1/P2.
6. **Автоматизируешь P0 и P1** — переиспользуешь существующие Page Objects, новые создаёшь только если нужно.
7. **Запускаешь тесты** локально — `npx playwright test`. Если падают — анализируешь причину, чинишь, перезапускаешь. Максимум 3 итерации, потом спрашиваешь меня.
8. **Создаёшь ветку** `qa/{TICKET}-short-description`, коммитишь по conventional commits (`test:`, `feat:`, `fix:`).
9. **Открываешь PR** через `github` MCP с шаблоном (см. ниже).
10. **Обновляешь тикет в Jira**: добавляешь комментарий со ссылкой на PR. Переводишь статус: если в workflow есть `In Review` — туда; если нет — в `Done` (потому что наша QA-часть готова, осталось только ревью PR людьми, что выходит за рамки тикета). Перед transition вызови `getTransitions` через MCP, чтобы увидеть доступные статусы.

## 5. Шаблон описания PR

```markdown
## Jira
[SCRUM-X](ссылка)

## Что сделано
- Тест-кейсы: `test-cases/SCRUM-X.md` (N кейсов: X×P0, Y×P1, Z×P2)
- Риск-анализ: `risks/SCRUM-X.md` (M рисков, top-3: ...)
- Автоматизировано: X из Y приоритетных кейсов

## Покрытие
- [x] Happy path
- [x] Negative cases
- [x] Boundary values
- [ ] Performance (требует отдельной задачи)
- [ ] Security: SQLi, XSS — описаны, но не автоматизированы

## Что НЕ покрыто и почему
- ...

## Как запустить
\`\`\`bash
npx playwright test tests/specs/SCRUM-X.spec.ts
\`\`\`

## Скриншоты / артефакты
См. `exploration/SCRUM-X/`
```

## 6. Стандарты кода

- `async/await` везде, никаких `.then()`
- Селекторы только в Page Objects, никогда в спеках
- Приоритет селекторов: `data-testid` > `role` > `text` > `css`. CSS-классы — последний выбор.
- Каждый тест независим — никаких зависимостей от порядка выполнения
- `test.describe` группирует по фиче, не по типу теста
- `expect`-проверки осмысленные: `await expect(page.getByRole('button')).toBeVisible()`, а не `expect(true).toBe(true)`
- Нет `sleep`/`waitForTimeout` — только `waitFor` с условием

## 7. Правила безопасности (важно!)

- **Никогда не пушь напрямую в `main`** — только через PR
- **Никогда не закрывай Jira-тикеты резолвом без подтверждения** — статус `Done` ставить можно (это окончание QA-части), но resolution оставлять `Unresolved` пока человек не ревьюнул PR
- **Не удаляй существующие тесты** без явного запроса
- **Не коммить секреты** — `.env` в `.gitignore`, для CI используй GitHub Secrets
- **MCP write-операции** (создание PR, изменение Jira) — только после моего подтверждения, если это первая операция в сессии

## 8. Cross-review с Codex (важная часть процесса)

После того как Claude Code открывает PR, я отдельно прошу Codex/ChatGPT сделать ревью того же PR с другим фокусом:
- Codex смотрит на код тестов: читаемость, дубли, антипаттерны
- Claude (в GitHub Action) смотрит на покрытие требований и риски

Это даёт **двойной независимый ревью** — снижает риск галлюцинаций одной модели.
В описании PR явно укажи: «Awaiting cross-review from Codex on code quality».

## 9. Когда чего-то не знаешь

- **Не выдумывай** селекторы, методы API, версии библиотек
- Если сомневаешься — открой через `playwright` MCP реальную страницу и посмотри
- Если не хватает контекста по фиче — спроси меня, не угадывай
- Если требование в Jira противоречит реальному поведению сайта — это **баг или устаревшее требование**, обязательно зафлажь это
